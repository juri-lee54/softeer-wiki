# DE : How Spark Works Internally: RDD and DAG

## Why RDD?

### What was the problem in Hadoop/MapReduce?

- 모든 **MapReduce 작업**은 각 단계(**Map → Shuffle → Reduce**) 사이에서 **중간 데이터를 디스크에 저장한다.**
- 이러한 **디스크 중심(I/O 중심)** 처리 방식은 다음과 같은 문제를 발생시킨다.
    - **디스크 읽기/쓰기(I/O)** 작업이 반복되어 **높은 지연 시간(Latency)** 이 발생한다.
    - **작업 간 데이터를 재사용할 수 없다.** 따라서 매번 **HDFS에서 데이터를 다시 읽거나 처음부터 다시 계산해야 한다.**
    - **머신러닝, 그래프 처리와 같은 반복적인 알고리즘**을 효율적으로 지원하지 못한다.

<br>

### The Redundancy Problem in MapReduce

- **K-Means 클러스터링과 같은 머신러닝 알고리즘**은 동일한 데이터를 **10~100회 이상 반복적으로 처리**하는 경우가 많다.
- 그러나 **MapReduce에서는 각 반복이 새로운 작업(Job)으로 실행된다.** 따라서 매 반복마다 **HDFS에서 동일한 데이터를 다시 읽고, 연산을 수행한 뒤, 중간 결과를 다시 디스크에 저장해야 한다.**
- 이러한 방식은 **디스크 입출력(I/O)을 과도하게 발생시켜 심각한 I/O 병목 현상(Bottleneck)을 초래한다.**

<br>

### No Support for Data Reuse in MapReduce

- 예를 들어, 데이터셋에 대해 **텍스트 토큰화(Tokenization)** 와 **데이터 정제(Cleaning)** 와 같은 전처리를 수행했다고 가정한다.
- 이후 이 전처리된 데이터를 **단어 빈도 분석(Frequency Count)** 과 **감성 분석(Sentiment Analysis)** 에 모두 활용하고자 한다.
- 그러나 **MapReduce에서는 각 작업(Job)마다 동일한 전처리를 다시 수행해야 한다.** 또는 전처리 결과를 **디스크에 직접 저장한 뒤 다시 불러와야 한다.**
- 이러한 방식은 **불필요한 디스크 입출력(I/O)을 증가시키며, 처리 지연(Latency)과 시스템 복잡도를 높인다.**

<br>

### Motivation for RDDs

- MapReduce의 중복 연산 문제와 메모리 기반 데이터 재사용 부재를 해결하기 위해 RDD가 도입되었다.

<br>

### What did Spark do differently?

- Spark는 **RDD(Resilient Distributed Dataset, 탄력적 분산 데이터셋)** 를 도입하였다. RDD는 **변경 불가능(Immutable)** 한 분산 데이터 컬렉션으로, 여러 처리 단계에 걸쳐 **메모리에 저장하여 재사용**할 수 있다.
- RDD는 다음과 같은 기능을 지원한다.
    - **메모리 기반 캐싱(In-memory Caching)** 을 통한 데이터 재사용
    - **복제(Replication)** 대신 **Lineage(계보 정보)** 를 이용한 장애 복구(Fault Tolerance)
- RDD의 핵심 장점
    - **디스크 입출력(I/O) 오버헤드를 크게 줄일 수 있다.**
    - 따라서 **반복적인 연산(Iterative Workload)** 이나 **대화형 분석(Interactive Workload)** 에서 높은 성능을 제공하며, 이는 기존 MapReduce가 효율적으로 처리하지 못했던 영역이다.

<br>

### RDD(Resilient Distributed Dataset)

- **RDD(Resilient Distributed Dataset, 탄력적 분산 데이터셋)** 는 **Apache Spark의 기본 데이터 단위**이다.
- RDD는 **클러스터의 여러 노드에 분산되어 저장되는 데이터 컬렉션(Collection)** 이다.
- RDD의 중요한 특징 중 하나는 **병렬 처리(Parallel Processing)를 지원한다는 점**이다. 따라서 여러 노드에서 데이터를 동시에 처리하여 성능을 향상시킬 수 있다.
- RDD는 **불변(Immutable)** 객체이다. 즉, 한 번 생성된 RDD는 직접 수정할 수 없으며, 기존 RDD에 **변환(Transformation)** 연산을 적용하여 새로운 RDD를 생성하는 방식으로 데이터를 처리한다.

<br>


### Creating RDD

Spark에서는 다음과 같은 방법으로 **RDD를 생성**할 수 있다.

1. **병렬화된 컬렉션(Parallelized Collections)**
    - 프로그램에서 생성한 **리스트(List), 배열(Array)** 과 같은 컬렉션을 여러 노드에 분산하여 RDD로 생성하는 방법이다.
2. **외부 데이터셋(External Datasets)**
    - **HDFS, 로컬 파일 시스템, Amazon S3** 등의 외부 저장소에 있는 데이터를 읽어 RDD를 생성하는 방법이다.
3. **기존 RDD(Existing RDDs)**
    - 이미 생성된 RDD에 **변환(Transformation)** 연산을 적용하여 새로운 RDD를 생성하는 방법이다.

### Lazy Evaluation

- **Spark의 지연 평가(Lazy Evaluation)** 란 **RDD에 대한 변환(Transformation) 연산을 즉시 실행하지 않는 방식**을 의미한다.
- 대신 Spark는 각 RDD에 적용된 연산들의 **계보(Lineage)** 정보를 기록해 두고, **액션(Action) 연산이 호출될 때까지 실행을 보류한다.**
- 이러한 방식은 Spark가 **실행 계획(Execution Plan)을 최적화**하고, **불필요한 연산을 최소화**할 수 있도록 한다.
- 비용이 저렴한 연산을 먼저 실행
    - 대한민국 국민 35세 이하  ← 이걸 먼저 연산하는 것이 비용이 저렴하다
    - 성이 ‘ㄱ’으로 시작

### Transformation vs Action

**Transformation**

- **Transformation**은 기존 RDD의 데이터를 가공하여 **새로운 RDD를 생성하는 연산**이다.
- 이러한 연산은 **지연 평가(Lazy Evaluation)** 방식으로 동작하며, **새로운 RDD, DataFrame 또는 Dataset**을 반환한다.
- 대표적인 예로는 **`map`**, **`filter`**, **`flatMap`**, **`groupBy`** 등이 있다.
- Transformation은 **즉시 실행되지 않으며**, **Action 연산이 호출될 때 비로소 실행된다.**

**Action**

- **Action**은 새로운 RDD를 생성하지 않고, **데이터에 대한 연산 결과를 반환하거나 외부 저장소에 저장하는 연산**이다.
- Action이 호출되면 그동안 정의된 **Transformation들이 실제로 실행**된다.
- 대표적인 예로는 **`collect`**, **`count`**, **`saveAsTextFile`**, **`reduce`** 등이 있다.

<br>

### Narrow & Wide Transformations

**Narrow Transformation**

- **Narrow Transformation**은 **각 입력 파티션의 데이터가 하나의 출력 파티션에만 전달되는 변환 연산**이다.
- 대표적인 예로는 **`map`**, **`filter`**, **`flatMap`** 등이 있다.
- Narrow Transformation은 **파티션 간 데이터 셔플(Shuffle)이 발생하지 않으므로**, 여러 파티션에서 **병렬로 처리할 수 있어 실행 효율이 높다.**

**Wide Transformation**

- **Wide Transformation**은 **하나의 입력 파티션의 데이터가 여러 출력 파티션으로 분산될 수 있는 변환 연산**이다.
- 대표적인 예로는 **`groupBy`**, **`reduceByKey`**, **`join`** 등이 있다.
- Wide Transformation은 **파티션 간 데이터 셔플(Shuffle)이 필요하며**, 이 과정에서 **노드 간 데이터 이동(Network I/O)** 이 발생할 수 있다.
- 따라서 Narrow Transformation에 비해 **실행 비용이 크고 성능 저하가 발생할 가능성이 높다.**

### Partition

- **Partition**은 Spark에서 데이터를 **논리적으로 나눈 작은 단위**로, 데이터를 여러 부분으로 분할하여 **병렬 처리**를 가능하게 한다.
- **각 파티션은 하나의 Executor에서 하나의 Task에 의해 처리**된다.
- Spark는 **데이터의 크기와 사용 가능한 클러스터 자원(CPU 코어 수 등)** 을 고려하여 **파티션의 개수를 자동으로 결정**한다.

<br>

### Shuffle in Spark

- **Shuffle**은 데이터를 **병렬로 처리하기 위해 클러스터 내 여러 워커 노드에 데이터를 재분배하는 과정**이다.
- Shuffle은 일반적으로 다음과 같은 경우에 발생한다.
    - **데이터가 파티션 간에 고르게 분산되지 않은 경우(Data Skew)**
    - **데이터를 특정 기준으로 재배치하여 처리해야 하는 경우**
    - **파티션 간 데이터를 집계(Aggregation)하거나 조인(Join)해야 하는 경우**로, 클러스터의 여러 노드 간 데이터 이동이 필요할 때
    - **하나의 노드 메모리만으로 처리할 수 없을 정도로 데이터가 큰 경우**
- **DAG(Directed Acyclic Graph)** 에서 **Exchange** 연산은 **Shuffle**을 의미한다. 즉, **클러스터 내 여러 노드 간에 실제 데이터가 이동하는 물리적인 데이터 전송 과정**을 나타낸다.

### Executing Spark Jobs

- **`spark-submit`** 을 실행하면 먼저 **Driver 프로그램**이 시작된다.
- Driver 프로그램은 **클러스터 매니저(Cluster Manager)** 에 필요한 자원(Resource)을 요청하는 동시에, **사용자가 작성한 메인 프로그램을 실행**한다.
- 프로그램이 실행되면 **SparkContext**가 생성되며, 이를 통해 **Transformation**과 **Action** 연산이 관리된다.
- **Action 연산이 호출되기 전까지는 Transformation 연산이 실제로 실행되지 않는다.** 대신 모든 Transformation은 **DAG(Directed Acyclic Graph)** 형태로 SparkContext에 저장되며, 이를 통해 **RDD Lineage(계보 정보)** 가 생성된다.
- **Action 연산이 호출되면 하나의 Job이 생성**된다.
- **Job**은 여러 개의 **Stage**로 구성되며, 각 **Stage**는 여러 개의 **Task**로 나뉜다.
- 생성된 Task는 **Task Scheduler**의 관리 아래 **클러스터 매니저를 통해 각 Worker 노드에 할당되어 병렬로 실행**된다.

<br>

- **DAG Scheduler**는 **RDD Lineage**를 실제 실행 가능한 **Task**로 변환하는 역할을 한다.
- 프로그램에서 정의된 **Transformation**을 기반으로 **DAG**를 생성하며, **Action**이 호출되면 DAG를 여러 개의 **Stage**로 분할한다.
- 각 Stage의 실행 준비가 완료되면 **Task Scheduler**에 전달되어 실행 가능한 **Task**로 스케줄링된다.
- 이후 Task는 **클러스터 매니저(Cluster Manager)** 를 통해 각 **Worker 노드의 Executor**에 할당되어 병렬로 실행된다.
- **클러스터 매니저**는 **자원(Resource) 할당**뿐만 아니라 **Job과 Task의 실행 상태를 관리 및 추적**하는 역할도 수행한다.
- **`spark-submit`** 을 실행하면 사용자 프로그램과 관련 설정 파일이 **클러스터의 모든 노드에 복사**된다.
- 따라서 각 Worker 노드의 Executor는 프로그램을 **로컬에서 직접 실행**할 수 있으며, 실행 과정에서 **추가적인 네트워크를 통해 프로그램을 가져올 필요가 없다.** 이로 인해 병렬 처리를 더욱 효율적으로 수행할 수 있다.

### Job

- **Job**은 **Action 연산**(예: `save()`, `collect()`)이 호출될 때 생성되는 **여러 개의 Task로 구성된 병렬 실행 단위**이다.
- Spark Shell과 같은 **대화형 환경**에서는 Driver가 사용자의 Spark 애플리케이션을 **하나 이상의 Job**으로 변환한다.
- 이후 Driver는 각 **Job을 DAG(Directed Acyclic Graph)** 로 변환한다.
- **DAG는 Spark의 실행 계획(Execution Plan)** 을 나타내며, DAG의 각 노드는 **하나 이상의 Stage**로 구성될 수 있다.
- 따라서 **Spark에서는 Action 연산이 호출될 때마다 새로운 Job이 생성된다.**

<br>

### Stage and Task

**Stage**

- **Stage**는 하나의 **Job을 여러 개의 Task 묶음으로 나눈 실행 단위**이다.
- 각 Stage는 **의존 관계**를 가지며, **DAG의 노드**로 구성된다.
- Stage는 **직렬(Serial)** 또는 **병렬(Parallel)** 로 수행 가능한 연산을 기준으로 생성된다.
- 모든 Spark 연산을 하나의 Stage에서 처리할 수 있는 것은 아니므로, **Shuffle과 같은 데이터 교환이 발생하는 지점**을 기준으로 **여러 개의 Stage로 분리**된다.
- 즉, **Stage는 Spark Executor 간 데이터 전송이 필요한 경계를 나타내는 실행 단위**이다.

**Task**

- **Task**는 **Spark Executor에서 실행되는 가장 작은 실행 단위(Unit of Execution)** 이다.
- 하나의 **Stage는 여러 개의 Task로 구성**된다.
- 생성된 Task는 여러 Executor에 분산되어 병렬로 실행된다.
- **각 Task는 하나의 데이터 파티션(Partition)과 1:1로 대응**하며, 해당 파티션의 데이터를 처리한다.

<br>

### Tasks and Stages in Spark

**Task와 Stage의 구성**

- **Task**는 **데이터 파티션(Partition)을 처리하는 가장 작은 실행 단위**이다.
- **Stage**는 **여러 개의 Task를 하나로 묶은 실행 단위**이다.
- 일반적으로 **`map`**, **`filter`** 와 같은 **Narrow Transformation**은 **Shuffle이 발생하지 않으므로 하나의 Stage에서 함께 실행**될 수 있다.

<br>

**Stage의 경계(Stage Boundary)**

- **Stage의 경계는 일반적으로 Shuffle이 발생하는 연산을 기준으로 결정된다.**
- 대표적인 예로는 **`reduceByKey`**, **`groupByKey`**, **`join`** 과 같이 **데이터를 파티션 간에 재분배(Shuffle)** 해야 하는 연산이 있다.
- 이러한 연산이 Spark Job에서 수행되면 **현재 Stage가 종료되고 새로운 Stage가 시작된다.**
- 즉, **Shuffle이 발생하는 시점이 Stage를 구분하는 기준**이 된다.

<br>

**Stage 실행 중 데이터 전송**

- **하나의 Stage 내에서는** 각 Task가 **클러스터에 이미 분산된 데이터 파티션(Partition)** 을 처리한다.
- 같은 Stage에 속한 Task들은 **각자의 파티션을 독립적으로 처리**하므로, **Executor 간 데이터 교환(Shuffle)이 필요하지 않다.**
- 하나의 Stage가 완료되어 **Shuffle 경계(Shuffle Boundary)** 에 도달하면, Spark는 **다음 Stage의 요구사항에 맞게 클러스터 전체의 데이터를 재분배**한다.
- **Spark Executor 간 데이터 전송은 주로 Shuffle 과정에서 발생**한다.
- 이 과정에서 각 Executor는 **다음 Stage를 수행하는 데 필요한 데이터 파티션을 서로 교환**하여, 이후 연산을 수행할 수 있도록 데이터를 재구성한다.

<br>

**성능에 미치는 영향**

- **효율적인 Stage 관리**는 **Spark 작업(Job)의 성능을 결정하는 중요한 요소**이다.
- **Stage의 개수를 최소화**하고 **데이터 파티셔닝을 최적화**하면, **Shuffle로 인한 오버헤드를 줄여 전체 실행 시간을 단축**할 수 있다.
- 또한 **Stage의 경계(Stage Boundary)** 를 이해하면 **불필요한 데이터 이동을 줄일 수 있으며**, 클러스터의 **자원 활용률(Resource Utilization)** 을 높여 Spark 작업의 성능을 향상시킬 수 있다.

<br>

## Why DAG?

### What was the problem in MapReduce job execution?

- **MapReduce Job**은 **Map → Reduce**로 이루어진 **엄격한 2단계 파이프라인** 구조를 가진다.
- 따라서 **Map → Reduce → Map → Reduce**와 같이 더 복잡한 처리를 수행하려면 **여러 Job을 연결(Chained Jobs)** 해야 한다.
- 이러한 방식은 다음과 같은 문제를 가진다.
    - **전체 작업을 전역적으로 최적화하기 어렵다.**
    - **Job 사이에 불필요한 대기 시간과 디스크 입출력(I/O)이 발생한다.**
    - **전체 데이터 흐름을 한 번에 파악하거나 관리할 수 없다.**
  
<br>

### Motivation for DAGs

- **MapReduce의 한 번에 하나의 Job만 처리할 수 있는 제약을 극복하기 위해 DAG가 도입되었다.**

<br>

### What did Spark do differently?

- **DAG(Directed Acyclic Graph, 방향성 비순환 그래프) 기반의 실행 방식**을 ****도입하였다.
- Spark는 실제 실행에 앞서 **여러 Transformation에 대한 Stage의 논리적 DAG를 생성**한다.
- 이를 통해 **전역적인 최적화**가 가능해진다. (예: Narrow Transformation의 파이프라이닝, Shuffle 최소화)
- DAG의 핵심 장점
    - **Stage 수를 줄이고, 디스크 입출력(I/O)을 최소화하며, 클러스터 자원을 더욱 효율적으로 활용할 수 있는 실행 계획을 수립할 수 있다.**

<br>

### DAG(Directed Acyclic Graph)

- **DAG**는 **Directed Acyclic Graph(방향성 비순환 그래프)** 를 의미한다.
- **Directed(방향성)** 는 **각 Edge가 명확한 방향을 가지는 것**을 의미한다. 이는 하나의 Vertex에서 다른 정점으로 **단방향으로 데이터가 흐름**을 나타낸다. 따라서 각 노드는 **이전 단계에서 다음 단계로 순차적으로 연결**된다.
- **Acyclic(비순환)** 은 **그래프에 Loop나 Cycle이 존재하지 않는 것**을 의미한다. 즉, 하나의 정점에서 다른 정점으로 이동한 후 **다시 처음 정점으로 돌아오는 경로가 존재하지 않는다.** 따라서 **한 번 수행된 Transformation은 이전 상태로 되돌아가지 않는다.**
- **Graph(그래프)** 는 **Vertex과 Edge으로 이루어진 구조**를 의미한다. 이러한 **정점과 간선이 일정한 순서로 연결된 형태**를 그래프라고 한다.

<br>

### Graph - Vertices and Edges

- 그래프는 활동의 순서를 나타낸다.
- 그래프는 여러 개의 원으로 이루어지며, 각 원은 하나의 활동을 나타낸다.
- 원들은 선으로 연결되며, 이 선은 한 활동에서 다른 활동으로 이어지는 실행 흐름을 나타낸다.
- 원은 **정점(Vertex, 복수: Vertices)** 이라 하고, 정점을 연결하는 선은 **간선(Edge, 복수: Edges)** 이라 한다.

### Why Spark Introduced RDDs and DAGs

| **Feature** | **MapReduce Limitation** | **Spark Solution** | **Result** |
| --- | --- | --- | --- |
| **Data Reuse** | No reuse; data must be recomputed | RDDs with caching | Faster iterative workloads |
| **Fault Tolerance** | Replication-heavy, slow recovery | RDD lineage | Lightweight, efficient recovery |
| **Execution Model** | Fixed Map→Reduce pipeline | DAG-based execution | Flexible, optimized workflows |
| **Multi-Stage Jobs** | Manual chaining, inefficient | Global DAG planning | Fewer I/Os, better performance |

## RDD vs DataFrames

### RDD vs DataFrames

- **RDD**는 Spark의 기본 데이터 구조이지만, **Low-level API**이므로 코드가 장황해지고, 상위 수준 데이터 구조에서 제공하는 최적화 기능을 활용할 수 없다.
- Spark는 **DataFrame**을 도입하여 보다 사용하기 쉽고 최적화된 API를 제공한다. **DataFrame**은 RDD를 기반으로 한 **High-level Abstraction**이며, 데이터가 **이름이 있는 Column** 형태로 구성되어 관계형 데이터베이스의 테이블과 유사한 구조를 가진다.
- DataFrame 연산은 Spark SQL의 최적화 실행 엔진인 **Catalyst**의 지원을 받으므로 계산 효율이 향상되어 성능이 개선될 수 있다.
- DataFrame에서도 RDD와 마찬가지로 **Transformation**과 **Action** 연산을 수행할 수 있다.
- **DataFrame**은 상위 수준의 API와 다양한 최적화 기능을 제공하므로, 일반적으로 **사용이 더 쉽고 성능도 더 우수하다.**
- 반면 **RDD**는 저수준 데이터 구조이므로 **Custom Operation**을 구현하거나 복잡한 데이터 처리 작업을 디버깅할 때 여전히 유용하다. 또한 **Partitioning**과 **Memory Usage**을 더욱 세밀하게 제어할 수 있다.
- **Text Stream, Binary File, Custom Format**과 같은 **비정형 원시 데이터(Raw, Unstructured Data)** 를 처리할 때는 RDD가 더 유연하다. 미리 정의된 스키마가 없어도 데이터를 직접 Parsing하고 원하는 방식으로 처리할 수 있기 때문이다.
